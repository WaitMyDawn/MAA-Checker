# MAA-Checker —— Minecraft 整合包可行性检验器

**先把它真的启动一遍，再说它行不行。**

把你已经装好的整合包，用工具启动一次：它盯着日志看到底是"进主菜单了"还是"崩了、为什么崩"，
然后做**最小改动**把包修到能进主菜单——每一步都记在台账里，不满意随时一键还原。

> 它跑在**你自己的电脑上**（不是服务器）。所以"能不能进主菜单"这个结论，天然就是
> "**你这台机器上**能不能进主菜单"——包括你用的 Java、显卡、内存、代理线路。

## 它能帮你做什么

**一句话：它就是那个"帮你把启动失败的整合包点开、看它炸在哪儿、然后动手修"的人——只不过全程留证据、可回滚。**

它同时对三类人有用：**被别人的整合包卡在启动界面的玩家**、**想在上架前先验一遍的整合包作者**、
**要帮人远程排查的服主**——因为结论是"这台机器上跑得起来/跑不起来"，而不是一句空泛的"应该没问题"。

### 三个最常见的场景

| 你遇到的情况 | 它会做什么 |
|---|---|
| 整合包启动就崩，启动器只说"游戏崩溃了"，看不懂日志 | 启动游戏、抓日志与崩溃报告，把**报错原文**翻译成"缺前置 / 加载器太旧 / Mixin 冲突 / 模组自身加载失败…"，再决定修哪一步 |
| 报错说缺某个必需前置（日志里是 `Missing or unsupported mandatory dependencies`，明细点名 `Mod ID: 'relics'`） | 去 Modrinth 找、下载、**核对 jar 里的 modId**，确认是这个模组才装进 `mods` |
| 包能启动但你没底，想知道到底稳不稳 | `--check "<实例名>" --repeat 4`：连跑 4 次给稳定性结论（整合包崩溃常常是竞态，跑一次通过说明不了什么） |

### 它不是什么

- **不是启动器**：它不负责给你装游戏、配 Java、管账号，它只管"检验 + 修"。
- **不是模组管理器**：它不会顺手给你装好玩模组，只补**日志明确说了缺的必需前置**。
- **不判断"好不好玩"**：只验证到**能进主菜单**（详见[已知限制](#已知限制诚实边界)）。

## 快速上手

### 1. 挑一个版本解压

| 版本 | 内容 | 需要 |
|---|---|---|
| **exe 版**（推荐） | 单个 `MAA-Checker.exe`（jar 已嵌在 exe 里） | 系统里有 **Java 21+**（找不到会弹出带下载指引的提示） |
| **lite 版** | `maa-checker.jar` + `launch.bat` | 同上；`launch.bat` 会自动找 Java（含 HMCL 自带运行时） |
| **自带运行时版** | `MAA-Checker.exe` + `runtime\` | **什么都不需要**，零依赖，代价是包大（约 55MB） |

### 2. 打开 → 选实例 → 点按钮

1. 双击 `MAA-Checker.exe`（lite 版则双击 `launch.bat`）→ 打开图形界面；
2. 它会自动探测 `%APPDATA%\.minecraft` 并列出实例；不是这个目录就点【浏览…】自己选
   （选到 `.minecraft` 那一层就行，里面要有 `versions`）；
3. 先点 **【开始检验】**（只跑一轮、不改任何文件），看看报告里说了什么；
4. 想让它自己动手就点 **【自动修复】**：它会按"补装 → 补不到才摘除"的顺序一轮一轮修，
   每轮都会重新启动验证，直到进主菜单为止。

> 第一次用建议：**先【开始检验】，再【自动修复】**。先看结论能让你知道它准备动什么。

### 3. 不满意就还原

所有改动都会出现在界面下方的"台账"区，点 **【还原到检验前】** 就能全部回滚
（补装的删掉、摘除的移回、升过的加载器还原、墓碑清空）。

### 界面速览

窗口分三块，从上到下：

| 区域 | 有什么 |
|---|---|
| **① 选择要检验的整合包实例** | 游戏目录、实例下拉、游戏内存、**自动修复轮次上限**、网络状态（检测网络 / 设置代理…） |
| **② 运行进度与实时日志** | 进度条 + 状态 + 实时日志。**它每一步在做什么都会打在这里**（含"为什么这么判"） |
| **③ 改动台账与还原** | 每轮的改动清单（点开看详情：改了什么、依据什么报错、报错原文）、【还原到检验前】、【打开产物目录】 |

底部还有"网络不通时：[询问我 / 只做摘除 / 直接中止]"——决定下载不通时它该怎么办。

## 它是怎么根据崩溃信息修好的（原理）

这一节讲清楚"它凭什么这么判"。看完你会知道它**什么时候会停手问你**，也就知道怎么用最省心。

### 一、证据从哪来：三路信息源

修复动作**不是**靠猜、也不是靠"哪个模组看起来可疑"，而是靠下面三路证据交叉验证：

| 信息源 | 怎么来的 | 用来看什么 |
|---|---|---|
| **① 静态预检** | 直接开箱读 `mods/*.jar` 里的 `mods.toml`（含 JarJar 嵌套 jar），拿到每个模组"声明了什么 modId、依赖谁、要什么版本区间" | 事先体检：谁缺前置、谁要求更高版本的加载器。**同时生成依赖图**（后面判断"摘谁要连带摘谁"就靠它） |
| **② 启动日志** | 用自研的最小启动器把游戏启动起来，盯 `logs/latest.log` **和**客户端 stdout | 判定这一轮"过没过"，以及加载阶段到底哪一步炸了 |
| **③ 崩溃报告** | 实例里的 `crash-reports\crash-*.txt`（只认**本次启动新产生**的那份，不认上次留下的旧报告） | 日志没写清时兜底：崩溃描述 + `Caused by` 最底层原因 |

两个容易踩的坑，它已经处理掉了：

- **只读 `latest.log` 会漏诊**：FML 的故障明细（`-- Mod loading issue for: X --`）**只打在客户端 stdout 里**，
  所以那一路必须一起收；
- **日志新旧边界**：启动前记下 `latest.log` 的长度与前 200 字符，只有"头一致"才按偏移切出新增部分，
  否则整份当新日志。否则会出现"两次启动日志一模一样 → 切出空串 → 诊断成没问题"的假象。

### 二、一轮"过没过"怎么判

| 结论 | 判据 |
|---|---|
| ✅ **PASS** | 命中后期成功标记（`Sound engine started` / `OpenAL initialized` / 方块贴图图集创建完成）**并且**进主菜单后继续观察一段时间**没有崩溃**（默认 15 秒，`--grace` 可调）——防"刚进主菜单就炸" |
| ❌ **FAIL** | 命中 13 个确定性失败标记之一，或进程非 0 退出 |
| ⏱ **超时** | 到时限（默认 180 秒）既没成功也没失败标记——**不算通过**，继续按证据诊断 |

那 13 个失败标记是实测校准出来的，例如：
`Missing or unsupported mandatory dependencies`、`Mod loading issue for:`、`ModLoadingCrashException`、
`Loading errors encountered`、`A mod crashed on startup`、`Mixin apply failed`、`Incompatible mods found`、
`Crash report saved to`、`Exception in thread "main"` 等。

### 三、把报错原文翻译成"问题类别"

抓到证据后，它按**文本特征 + 依赖块结构**归类（不做语义猜测），归成 7 类：

| 你在日志/报告里能看到的原文（FML 打印的） | 工具判定为 | 它凭什么这么判 |
|---|---|---|
| `Missing or unsupported mandatory dependencies` + 明细块 `Mod ID: 'x', Requested by: 'y', Expected range: '...', Actual version: '[MISSING]'` | **缺必需前置** | 有完整字段：谁要、要谁、要什么区间、现在装没装 |
| 同样的明细块，但 `Mod ID` 是**加载器自己**（`neoforge`）或 `minecraft` 且版本是 `[MISSING]` | **加载器版本不足** | 缺的是底座，不是模组 → 该升加载器，而不是去 Modrinth 找 |
| `-- Mod loading issue for: X --` + `Failure message: …` / `Mod file: …` | **模组自身加载失败** | FML 已经点名到具体文件，构造期抛异常 |
| `Mixin apply failed` / `Mixin … from mod Y` | **Mixin 冲突** | 只有这一行确实出现在失败上下文里才算（Mixin 的 WARN 不算，见踩坑记录） |
| `Duplicate mods: …` | **重复模组/重复类** | 同一个 modId 或类被两个 jar 提供 |
| 依赖块里**其它模组**的版本区间不满足 | **版本区间不满足** | 静态/文本判定与真实加载器语义不完全一致 → **只提示、不自动动手** |
| `Exception in thread "main"` / `Crash report saved to` / crash-report 指认到某模组 | **其它启动崩溃** | 兜底：空指针、原生库、内存等，摘报错报告指认的那一个 |
| `IllegalArgumentException: 1-V1-1.21+: Empty pre-release`（只给了版本号，没给 modId） | **版本号格式非法** | 有模组声明了一个加载器解析不了的版本号。用这个版本号去反查"谁声明了它"——两条独立来源交叉验证，见下一节 |
| `Caused by: … Mixin … from mod X failed` 之类（崩溃链里点名了模组） | **崩溃链归因** | 从 `Caused by` 链里读出 `from mod X`，且 X 必须确实是已安装的模组 |
| `at TRANSFORMER/legendary_monsters@1.21.1/…`（堆栈帧里的模组层） | **堆栈归因** | 过滤掉 `minecraft`/`neoforge`/`java.*` 等框架帧后的第一个模组帧。最低置信，**每轮最多采纳一个** |

> 注意顺序：**静态预检负责"事先告诉你"和"提供依赖图"，真正驱动修复动作的是运行期证据。**
> 因为 jar 里写的依赖可能是动态的（`${file.jarVersion}` 这类占位符静态求不出来），
> 只有真的启动一次，才知道这台机器上到底炸在哪一步。

### 三之补：日志里没有 modId 时，它怎么反查"到底是谁"

有些崩溃**日志里根本没有模组名**（只给一个版本号、或只给一段堆栈），这时按下面的优先级反查——
顺序不能乱，乱了会摘错人：

| 优先级 | 渠道 | 怎么反查 |
|---|---|---|
| 1 | **版本号指纹**（最硬） | 从报错里抓到版本号（如 `1-V1-1.21+`），再去两处找"谁声明了它"：**①`latest.log` 里 FML 打印的模组清单行**（格式 `<显示名> <版本> (<modId>)`）；**② jar 里声明的版本**（扫 `mods/*.jar` 的 mods.toml / fabric.mod.json / quilt.mod.json）。两处都有就交叉验证，只有一个也照样定案 |
| 2 | **崩溃链归因** | 在 `Caused by` 链里找 `from mod X`（X 必须确实是已安装模组） |
| 3 | **堆栈归因**（最低） | 找第一个"非框架"的 `at TRANSFORMER/<modId>@…` 帧；也认 `in class 'a.b.c.Class'` 里的包名。**每轮最多采纳一个** |
| 4 | **崩溃报告兜底** | `Mod file:` 路径 → 文件名 → modId |

**为什么这个顺序不能反**（实测案例，2026-09-26 的"万象"包）：

```
顶层异常：MethodInvocationException … in class 'settingdust.preloading_tricks.neoforge.…'
Caused by：java.lang.IllegalArgumentException: 1-V1-1.21+: Empty pre-release   ← 根因在这
```

按堆栈帧看，会怀疑 `preloading_tricks`；可**摘掉它之后，同一个版本号错误照样出现**——它只是"报信者"。
真正的肇事者是 `panda-temple-V1-1.21+.jar`（modId `mr_panda_temple`）：它的 `neoforge.mods.toml` 里
写着 `version = '1-V1-1.21+'`。工具现在的输出是：

```
[BAD_VERSION_FORMAT] modId=mr_panda_temple jar=panda-temple-V1-1.21+.jar
归因过程：版本号 1-V1-1.21+ 唯一指向 mr_panda_temple（来源：jar 声明版本）
         栈帧/类名候选 preloading_tricks（已由版本号指纹定位到肇事模组，下面这些只是报信者，未采用）
计划动作：REMOVE_MOD | mr_panda_temple | panda-temple-V1-1.21+.jar
```

两点补充：

- 这类崩溃常常发生在**模组清单打印之前**（游戏在 `ModDiscoverer` 阶段就挂了），那时 `latest.log` 里
  根本没有清单行 —— 所以两条来源里真正靠得住的是 ② **jar 里声明的版本**，清单行是加分项。
- **只在报错后才做这件事**：工具**不会**提前扫描"谁的版本号格式不合法"（那是加载器自己的判据，
  静态猜不准，也不该替它下结论）；jar 里的声明版本只在**出错后**用来反查是谁。
- **反查不到就不动手**：两条来源指向不同模组、或指向多个模组时，一律转人工，绝不按文件名硬猜。

### 四、每类问题 → 最小动作

顺序固定 **A → B → C**：**先补装，补不到才摘除**。

| 动作 | 做什么 | 什么时候会选它 |
|---|---|---|
| **A 升级加载器** | 就地升级 NeoForge 到满足要求的最新版（改实例版本 JSON，库写进 `libraries/`） | 判定为"加载器版本不足"时。**目前只支持 NeoForge**；Forge/Fabric/Quilt 会明确转人工 |
| **B 补装前置** | 从 Modrinth 找 → 下载 → **核对 jar 内真实 modId** → 装进 `mods` | 判定为"缺必需前置"时。找不到、或候选都对不上 → 见下面的底线 |
| **C 摘除模组** | 把模组**移到** `bin\<实例>\round-N\`（不是删除），并在台账里写下问题类别 + 原因 + **报错原文** | 模组自身加载失败 / Mixin 冲突 / 重复模组 / 其它崩溃；以及"前置补不上，删掉需要它的模组" |
| **D 不做取舍** | 不判断"哪个模组是核心"，只按"能不能让它跑起来"办 | —— 这是价值观，不是动作 |

**为什么"补装"能保证装的是对的**：Modrinth 的项目/版本接口里**没有 modId 字段**，所以流程是
"slug 直查 → 搜索回退 → 三道闸门（**必须是真 mod**、**loader 严格一致**（neoforge 与 forge 互斥，
不互相通融）、当前环境**有可用 jar**）→ 下载后读 `META-INF/mods.toml` / `fabric.mod.json` 核对 modId"。
**对得上才装**。同名模组很常见（比如 `relics`），这一步就是为它们准备的。

### 五、三条"宁可不修，也不乱动"的底线

这三条是刻意的设计取舍，遇到时它会**停下来把情况写清楚**，而不是硬修：

1. **不确定是哪一个，就不动手**：候选 jar 里没有一个声明所需的 modId（重名模组）时，
   **既不安装，也不摘除依赖方**，把候选清单列给你确认。
2. **网络不通 ≠ 模组不存在**：下载/查询失败一律不当作"补不到前置"去摘模组——
   否则你在咖啡厅没连上网，回家就发现包里少了几个模组。
3. **判不准的区间不下结论**：版本区间的比较规则和真实加载器语义不完全一致，
   所以"区间不满足"这类只有文本证据的问题只提示，交给人工。

另外两条护栏：

- **墓碑机制**：凡被判要移除的模组进墓碑，后续轮次**永不允许再装回**——否则会出现
  "A 需要 B → 装 B → B 导致崩溃 → 删 B → 下一轮又装上 B"的死循环；
- **级联上限 40**：一次级联摘除超过 40 个模组就不自动执行，转"需人工确认"（防止一次误判毁掉半个包）。

### 六、一轮一轮收敛

每一轮都是："启动 → 判读 → 诊断 → 按 A/B/C 动手 → 落台账 → 再启动"。什么时候停：

- ✅ 进主菜单 → 结束（退出码 0）
- ⛔ 这一轮**没有任何改动可做**（继续跑只会重复同样的失败）→ 停下
- ⛔ 需要人工处理（级联超限、只支持 NeoForge 的升级、同名模组对不上）→ 停下并写清原因
- 🔄 **轮次用完还没修好** → 问你：**追加轮次 / 停止（保留改动）/ 停止并还原**
  （默认 4 轮只是起点，界面里能改，硬上限 20；无人值守时不会挂住，按"停止"处理）

### 真实例子：两条都来自实际跑过的包

**例 1：缺前置。** 报告里出现这样一条：

```
## 动作B 补装前置：relics
- 问题类别: MISSING_REQUIRED
- 原因: reliquified_irons_spells_and_spellbooks 缺少必需前置 relics（要求 [0.12.3,)）
```

它的动作序列是：从日志里读到"谁要谁、要什么区间" → 去 Modrinth 解析 `relics` →
排除一个同名的无关项目（`loaders=[datapack]`，不是 mod）→ 回退搜索命中 `relics-mod`
→ 取满足 `[0.12.3,)` 的最新版 `0.12.8` → 下载后核对 jar 内声明的 modId 是 `relics` → 装进 `mods`。
台账里你会看到"已从 Modrinth 补装 relics-mod 0.12.8（jar 内 modId 已核对）"。

**例 2：多轮收敛。** 故障包 `铁魔法冒险之旅`（基线 80 模组 / loader 21.1.231）：

```
第 1 轮：A 升加载器 + B 补前置（0 摘除）
第 2 轮：补 rhino
第 3 轮：PASS（66.3s，证据 Sound engine started）
```

修好之后再看 `--restore`：mods 从 83 回到 80、loader 回到 21.1.231、墓碑清空。

## 安全性：它动了什么、怎么还原

| 它可能做的改动 | 具体动作 | 怎么还原 |
|---|---|---|
| 升级加载器 | 改实例的版本 JSON | 原 JSON 有备份，台账记着"从什么切到什么" |
| 补装前置 | 往 `mods` 里**新增**一个文件（下到 `state\<实例>\cache\` 后复制进来） | 台账记着文件路径与哈希 → 还原时删除 |
| 摘除模组 | **移动**到 `bin\<实例>\round-N\`（不是删除） | 还原时移回原位（同名冲突会加时间戳，绝不覆盖） |

台账是**双份**的：`state\<实例>\<会话>-round-N.json`（给程序读）+ 同名 `.md`（给人读）。
界面上点开就能看到"改了什么、依据哪条报错、报错原文是什么"。

> 换句话说：**它没有"直接删掉你的模组"这种操作**，最坏情况也只是把文件挪进 `bin\` 等着你搬回去。

## 和 HMCL 的关系（**用 HMCL 启动的包请务必看**）

如果你这个整合包是**用 HMCL 导入的整合包**（实例目录里有 `modpack.cfg`），只修文件系统是不够的：

> **HMCL 每次点【启动】都会先跑一次"整合包补全"，按包内清单把缺的文件下载回来。**
> 也就是说：它会把我们刚摘掉的模组**原样补回来**，等于白修。

这不是猜测，是 HMCL 自己日志里的原文（实测 2026-09-26，"万象"包）：

```
[12:15:38] [LauncherHelper.launch/INFO] Launching game version: 万象
[12:15:38] [TRACE] Executing task: org.jackhuang.hmcl.modpack.modrinth.ModrinthCompletionTask
[12:15:38] [FileDownloadTask.beforeDownload/TRACE] Downloading https://cdn.modrinth.com/data/z0qJSbtP/.../panda-temple-V1-1.21%2B.jar
                to D:\...\versions\万象\mods\panda-temple-V1-1.21+.jar
[12:15:45] [TRACE] Task finished: 下载整合包相关文件
```

清单来自实例目录下的 `modpack.cfg`（HMCL 的整合包标记，内嵌一份 Modrinth manifest：194 条 `files[]`，
每条带 `path` + 哈希 + 下载地址）。

**本工具的处理方式**：在一次修复**真的改动了文件**之后，自动把标记文件改个名：

```
modpack.cfg  →  modpack.cfg.maa-checker-bak      （内容一字未改）
```

改名后 HMCL 不再把它当整合包，也就不再跑补全任务——我们摘掉的模组就留得住了。
这件事会在**修复报告**（`fix-summary.md`）和日志里写明，界面上还会**弹窗解释原因**。

两点要知道：

- **代价**：HMCL 里【更新整合包】的入口会消失（那个功能本来就会把你修好的包覆盖回去）。
- **恢复**：点【还原到检验前】（或 `--restore`）会**自动把文件名改回去**；也可以手动改回 `modpack.cfg`。

> 顺带一提：HMCL 的补全**只增不删**（日志里只有下载、没有删除），所以本工具**补装**的模组它不会动；
> 只有**摘除**会被它撤销。

## 常见问题（FAQ）

**Q：国内要开代理吗？**
找模组地址那一步走镜像（实测 0.065s，稳定）；但**下载文件**建议开代理（Clash/V2Ray 打开系统代理即可）。
工具会自动探测代理，也会在下载不通时弹窗让你选：继续 / 只做摘除 / 停止并还原。详见[网络与代理](#网络与代理国内用户请读)。

**Q：它会不会把我的模组删了？**
不会。摘除 = 移到 `bin\<实例>\round-N\`；补装 = 新增文件；升级加载器 = 备份后改 JSON。都能一键还原。

**Q：一次要多久？**
一轮 = 启动游戏 + 观察。实测健康包 35~45 秒；修复每轮 40~90 秒（还要加下载时间）。
包越大、模组越多，启动越慢。

**Q：我点了修复，但最后没修好，怎么办？**
看两处：界面日志（会写"为什么停下来"）和台账（每轮做了什么）。然后三选一：
追加轮次重跑（`--rounds 8`）、按日志提示手工换版本、或者【还原到检验前】回到原样。

**Q：我用 HMCL 启动后，刚被摘掉的模组又自己回来了？**
那是 HMCL 的"整合包补全"（它按 `modpack.cfg` 里的清单把缺失文件下回来）。本工具在一次真的改动了文件的
修复之后，会自动把 `modpack.cfg` 改名为 `modpack.cfg.maa-checker-bak` 来阻止这件事，并在报告与弹窗里说明。
详见 [和 HMCL 的关系](#和-hmcl-的关系用-hmcl-启动的包请务必看)。

**Q：提示"疑似游戏正在运行"？**
它发现 `logs/latest.log` 在 10 秒内还被写过——先关掉游戏再跑。确认没有游戏在跑就继续（跳过这道闸）。

**Q：支持 Forge / Fabric / Quilt 吗？**
**启动检验与诊断与加载器无关**（能识别到实例就能跑）；补前置也一样走 Modrinth。
但**加载器的就地升级目前只支持 NeoForge**，其它加载器会明确告诉你"转人工"。

**Q：它说"能进主菜单"，就等于这个包没问题吗？**
不等于。它只验证到主菜单（不进世界、不长时间挂机），详见[已知限制](#已知限制诚实边界)。

**Q：杀了毒之后游戏报"找不到主类 BootstrapLauncher"？**
那是共享库目录 `libraries/` 被清掉了。用 `--repair-libraries "<实例名>"` 按版本 JSON 的
url + sha1 补回来（只增不改不删）。

**Q：它会不会自己乱装模组？**
只装日志明确说"缺的必需前置"，而且装之前会核对 jar 里的 modId；同名模组对不上就不装、
也不摘依赖方，交给你确认。

## 命令行参考（进阶 / 自动化）

图形界面之外，所有能力都有等价的命令行入口（排查、自动化、CI 都靠它）：

| 命令 | 作用 |
|---|---|
| `--gui` | 打开图形界面（不带任何参数也是这个） |

| `--scan <实例>` | 静态依赖预检（只读，不启动、不改文件） |
| `--check <实例>` | 跑一轮：静态预检 → 启动 → 盯日志 → 诊断 → 报告 |
| `--check <实例> --repeat N` | 连跑 N 次给稳定性结论（整合包崩溃常是竞态，单次通过说明不了稳定） |
| `--fix <实例>` | 自动闭环修复（A/B/C 依次执行，修完再跑一轮） |

| `--test-proxy` | 三步实测网络：搜索接口 / 版本解析 / **真下载一份 jar** |
| `--probe-dep <modId>` | 只解析 `modId → 候选项目 → 版本 → 文件`（打印闸门淘汰依据与候选清单），不下载、不改文件 |
| `--diagnose <文件>` | 离线诊断已有 `latest.log` / 客户端 stdout / 崩溃报告（可逗号分隔多个） |
| `--set-proxy <地址>` / `--clear-proxy` / `--no-proxy` | 代理设置（写进 `config.properties`） |
| `--net ask\|remove-only\|abort` | 网络不通时：询问我 / 只做摘除不补装 / 直接中止 |
| `--mx 3G` `--timeout 180` `--grace 15` `--retry 1` `--cascade-limit 40` | 各阶段参数 |
| `--rounds N` | 自动修复的**初始**轮次上限（默认 4，上限 20；跑完还会问是否追加） |
| `--on-exhausted ask\|stop\|restore` | 轮次用完仍未通过时：询问我 / 停止保留改动 / 停止并还原（默认 ask；无交互终端时按 stop 处理） |

## 网络与代理（国内用户请读）

**实测结论**（2026-09-22）：

| 线路 | 实测 |
|---|---|
| Modrinth **信息**接口 `api.modrinth.com` 直连 | 时通时不通（0.69s ~ 连接超时） |
| **镜像信息接口** `mod.mcimirror.top/modrinth` | **0.065s，稳定**（比官方快 10 倍，不受墙） |
| **下载 CDN** `cdn.modrinth.com` 直连 | 4 次里 3 次连不上；通了也只有几 KB/s（307 跳 `cdn-alt` 后基本停滞） |
| 走代理（Clash 7890）下载同一文件 | 2.29MB / **1.9 秒**（≈1.2MB/s） |
| 镜像**文件**入口 `mod.mcimirror.top/data/...` | **302 跳回官方**——镜像只加速"找地址"，**不承运文件** |
| 对照：`maven.neoforged.net`（加载器） | 3 秒下完 7MB（说明线路本身没问题） |

### 工具的网络策略

| 情况 | 走哪条路 |
|---|---|
| **有可用代理** | 下载走**官方本站（经代理）**；API 仍优先镜像（快），失败自动回退官方 |
| **没有代理** | API 走镜像（保证"找地址"这一步不受墙）；下载**先试镜像文件入口**（0.1 秒判死）→ 再试直连官方 CDN（**5 秒稳定判据**）→ 都失败就弹窗 |

### 五个关键设计

1. **代理三层探活**：端口在听 → 隧道能建 → **真能访问 Modrinth**，三层都过才算"有代理"。
   实测踩过的坑：Clash 进程在跑、7890 在听，但出口节点挂了（经它访问百度 200/0.2s，访问 Modrinth 全部超时）——
   只看端口会把"假代理"当成可用，然后一路卡死。另外**不再只看系统代理注册表**：会主动扫本机常见代理端口
   （7890/7891/7897/10809/10808/2080/1080/8080），因为"端口开着但系统代理关着"是最常见的状态。
2. **5 秒稳定判据**（不是"5 秒必须下完"）：连接超时 8 秒；连上后 **5 秒内平均速度 < 13KB/s 判"不稳定"**并立刻中止——
   由 curl 原生 `--speed-limit/--speed-time` 实现。大文件在"证明起得来"之后会给足时间下完
   （总时长兜底 `max(30s, 文件大小 ÷ 20KB/s)`），小文件秒完。
3. **通道互为兜底 + 判死记忆**：代理 ↔ 直连互相兜底；某条通道判死后**本轮不再重复试**——
   否则 10 个模组会白等 20 次（旧版"一直不动"的直接原因就在这里）。
4. **弹窗三个选项**：**已开好代理继续** / **本次只做摘除**（不再补装，缺前置就摘依赖方）/ **停止检验并还原**。
   没有代理时不会静默降级，而是把选择权交给你。
5. **绝不把"网络不通"当成"补不到前置"**去摘模组；JSON 响应做校验（拿到 HTML/劫持页会重试并换通道）。

> 两个隐藏开关：`--no-mirror`（禁用镜像，只用官方）、`--direct-cdn`（允许直连官方 CDN，默认关）。
> 镜像站可能失效，所以镜像失败会自动回退官方，并在日志里写明回退原因。

### 关于 libraries（共享地基，别乱删）

`<游戏目录>/libraries/` 是**所有实例共用**的库目录。它一旦被误删，**所有实例**都会起不来，
而且报错常常是"找不到主类 cpw.mods.bootstraplauncher.BootstrapLauncher"这种看不懂的样子。

- 本工具升级加载器时会往这里写库（运行时必需品，**不删**），并记进台账；
- 万一被删了：`--repair-libraries "<实例名>"` 一条命令按版本 JSON 的 url + sha1 补回来；
- **不要在 `libraries/` 或任何含目录链接（junction）的目录上用"递归删除"**：
  Windows 的 `Remove-Item -Recurse` / `rd /s` 会**穿透 junction** 把真实目录删空。
  （本工具早期版本用过 junction 沙盒，实测踩过这个坑，现已彻底不用链接。）

## 已知限制（诚实边界）

- 只验证到**"能进主菜单"**：能不能玩、好不好玩、后期内容有没有问题，工具不判断。
- **判据是按 1.21.1 + NeoForge 校准的**：成功/失败标记词表、加载器升级路径都来自实测；
  其它 MC 版本、Forge/Fabric/Quilt 实例一样能识别、启动、抓证据，但"升级加载器"这类动作会转人工。
- **只支持就地升级 NeoForge**；Forge / Fabric / Quilt 的加载器升级会明确转人工。
- 偶发竞态崩溃**只重试 1 次**（可配 0~3）：重试通过即保留该模组，只在台账里记风险。
- 级联摘除有上限（默认 40），超限转人工确认。
- **同名模组不替你做主**：候选 jar 里都对不上依赖声明的 modId 时，工具不装、也不摘依赖方，
  而是在日志/台账里列出候选清单让你确认。另外 jar 里读不到 `mods.toml`/`fabric.mod.json` 时
  一律按"无法确认"处理（不会当成校验通过）。
- **归因渠道分置信度**：版本号指纹 > 崩溃链 > 堆栈帧；堆栈归因这类低置信结论**每轮最多采纳一个**，
  其余留到下一轮。两条来源互相矛盾、或同时指向多个模组时，一律转人工——不按文件名硬猜。
- **不做 slug 后缀猜测**（如 `relics → relics-mod`）：作者习惯各不相同，猜错就会装错包；
  项目定位靠"slug 直查 + 搜索回退 + 闸门 + jar 内 modId 核对"四步，而不是名字变形。
- 版本区间判定用的是"数字序列比较"，与真实加载器的语义不完全一致，因此静态阶段
  **只把"缺前置 / 加载器版本不足"当高置信**，其余标记"需人工复核"。
- `${...}` 占位符无法静态求值（如 `slayersbeasts` 的 `${file.jarVersion}`），单独上报不静默放过。

### 踩坑记录（都写进了代码注释，改之前值得一看）

1. **日志新旧边界**：只用"末尾内容锚点"会切出空串 → 诊断变成"没问题"、修复闭环空转；
   只用"长度+末尾指纹"又会被"两次启动日志完全一样"骗过。最终方案 = **头部指纹 + 字符偏移**。
2. **字节 vs 字符**：日志里有中文路径，`Files.size()`（字节）与 `String.length()`（字符）能差几百，
   混用会让锚点永远对不上。
3. **Java 网络栈**：IPv6 直连 `maven.neoforged.net` 会 TCP 卡死（curl 两种栈都正常），
   需要强制 IPv4；而 Java 的 `connectTimeout/requestTimeout` 在"黑洞式阻断"下**不生效**
   （探针挂过 14 分钟），所以下载改成 **curl 优先** + 自己的看门狗。
4. **FML 故障明细只打在客户端 stdout**，不在 `latest.log`——只读 latest.log 会漏诊
   （明明有崩溃报告却报"没解析出故障"）。
5. **Mixin 的 WARN 不是故障**（`has multiple constructors ... was selected`），曾把无辜模组指成元凶。
6. **404 ≠ 网络故障**：一次正常的"探测 slug 存不存在"曾触发整轮转代理 + 弹窗。
7. **PowerShell 5.1 按 ANSI 读无 BOM 的 UTF-8 脚本** → 乱码语法错；`.ps1` 必须带 BOM，`.bat` 只用 ASCII。
8. **`$ErrorActionPreference='SilentlyContinue'` 会吞掉 `java -version` 的 stderr**（版本信息正好在 stderr），
   导致 Java 探测永远返回"没找到"。
9. **`java.util.Properties.store()` 会转义**（`D\:\\Minecraft`）且写 BOM，配置改成明文 UTF-8 并兼容读回老格式。
10. **slug 会撞名，别把"第一个 200"当答案**：`/v2/project/relics` 真的返回 200，但那是另一个
    `loaders=[datapack]` 的项目，真正的 Relics 在 `relics-mod` 下。旧实现命中即返回，于是把
    "这个项目没有 neoforge 版本"说成了"Modrinth 上没有这个前置"，进而误摘了依赖它的模组。
    修法是**候选链**：slug 直查的每个候选都要过闸门（真 mod + loader 严格一致 + 有可用 jar），
    过了还要在下载后核对 jar 内声明的 modId（Modrinth 接口没有 modId 字段，jar 里才有）。
11. **mods.toml 有两种写法，少认一种就等于"这个模组不存在"**：除了 `[[mods]]` 表头，
    还有内联数组 `mods = [ { modId = 'x', version = 'y', … } ]`（Modrinth 打包生成的模组常是这种，
    例如"万象"里的 `panda-temple-V1-1.21+.jar`）。旧解析器要求键在**行首**，而内联数组里所有键都在
    同一行 → 整个模组读不到。后果有两个：① 静态预检把依赖它的模组误判成"缺前置"；
    ② 拿不到声明版本，`Empty pre-release` 就没法反查肇事者。现在 toml 两种写法 +
    `fabric.mod.json` + `quilt.mod.json` 三条载体一起读（见 `JarModReader`）。
12. **"报信者"不是"肇事者"**：崩溃日志里最显眼的那个类名/堆栈帧，常常只是**调用方**。
    实测（万象包）：顶层是 `MethodInvocationException … in class 'settingdust.preloading_tricks…'`，
    真根因却在 `Caused by` 里的 `1-V1-1.21+: Empty pre-release`；摘掉 `preloading_tricks` 后错误照旧。
    所以归因必须**分优先级**（版本号指纹 > 崩溃链 > 堆栈帧），并且高优先级命中时，
    低优先级候选只能写进"归因过程"，不能变成动作。
13. **`Empty pre-release` 的 modId 不在报错里，但不用猜**：加载器抛异常时只带版本号，
    而 `latest.log` 里 FML 自己打印了模组清单（`<显示名> <版本> (<modId>)`，显示名可能带空格/颜色码，
    要**右对齐**解析），jar 里也有声明版本 —— 两条独立来源交叉验证即可定案。
14. **修完不算完：启动器会把摘掉的模组补回来**。HMCL 把导入的整合包记在 `modpack.cfg`（内嵌 Modrinth
    清单），**每次启动**都跑 `ModrinthCompletionTask` 按清单补全缺失文件——实测我们摘掉的 13 个模组
    在用户下次启动时被原样下载回来（HMCL 日志 12:15:38 → 12:15:45）。所以"摘除"必须配合
    **把整合包标记改名**（`modpack.cfg → modpack.cfg.maa-checker-bak`），否则修了等于没修；
    `--restore` 时会自动改回。附带教训：HMCL 的补全**只增不删**，所以"补装"是安全的。
15. **低置信归因要"点到为止"**：实测一次 Mixin 崩溃里，崩溃链（中置信）指向 `tensura_iron_spells`、
    堆栈帧（最低置信）指向 `aces_spell_utils`，两条都摘 → 后者进墓碑 → 下一轮又**连带**摘掉两个依赖它的
    模组，**一次误判摘了 3 个**。现在改为：**高优先级渠道一旦命中，低优先级只能写进"归因过程"、不许产生动作**，
    每轮只摘最可信的那一个，剩下的留给下一轮暴露。
